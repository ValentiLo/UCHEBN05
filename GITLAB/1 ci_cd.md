## **CI/CD: Непрерывная Интеграция и Непрерывная Доставка/Развертывание**

### **📌 Что такое CI/CD?**

**CI/CD** — это методология разработки программного обеспечения, которая помогает командам **часто и надежно** доставлять изменения кода. Состоит из двух основных компонентов:

### **1. CI - Непрерывная Интеграция (Continuous Integration)**

**Основная идея:** Частое объединение изменений кода от всех разработчиков в общую ветку с автоматической проверкой.

**Как это работает:**
- Разработчик делает изменения в своей ветке
- Создает Merge/Pull Request
- Автоматически запускается пайплайн, который:
  - Собирает приложение
  - Запускает тесты
  - Проверяет качество кода
- Если все проверки пройдены → изменения могут быть объединены

**Ключевые практики CI:**
```
📌 Частые коммиты (минимум раз в день)
📌 Автоматическая сборка и тестирование
📌 Быстрая обратная связь (не более 10 минут)
📌 Исправление сломанных сборок в приоритете
```

### **2. CD - Непрерывная Доставка (Continuous Delivery)**
**ИЛИ**
### **Непрерывное Развертывание (Continuous Deployment)**

**В чем разница?**

| **Непрерывная Доставка (Delivery)** | **Непрерывное Развертывание (Deployment)** |
|-------------------------------------|--------------------------------------------|
| Код **готов к развертыванию** в любой момент | Код **автоматически развертывается** в продакшен |
| Требуется **ручное подтверждение** для релиза | Развертывание происходит **полностью автоматически** |
| Больше контроля, безопасность | Быстрее обратная связь от пользователей |
| Подходит для: финансовых систем, мед. ПО | Подходит для: SaaS, веб-приложений |

**Визуализация процесса:**

```
[Разработчик]
    │
    ├── CI ────────────────────────────────┐
    │ 1. Коммит в репозиторий              │
    │ 2. Авто-сборка                       │
    │ 3. Авто-тестирование                 │
    │ 4. Проверка качества кода            │
    │                                      │
    ├── CD (Delivery) ─────────────────────┤
    │ 5. Деплой на тестовое окружение      │
    │ 6. Ручное тестирование (опционально) │
    │ 7. Кнопка "Развернуть в прод" ⚡     │
    │                                      │
    └── CD (Deployment) ───────────────────┘
        8. Автоматический деплой в прод ✅
```

### **🎯 Зачем нужен CI/CD?**

| **Проблема без CI/CD** | **Решение с CI/CD** |
|------------------------|---------------------|
| "У меня на машине работает!" | Единая среда сборки для всех |
| Ручное тестирование занимает дни | Автоматические тесты за минуты |
| Выпуск релиза раз в месяц/квартал | Возможность выпускать несколько раз в день |
| Страх вносить изменения | Уверенность благодаря автоматическим проверкам |
| "Кто сломал сборку?" | Мгновенное определение виновника |

### **🛠️ Ключевые компоненты CI/CD пайплайна**

**Типичные стадии CI/CD пайплайна:**

```yaml
stages:
  - .pre           # Подготовка (инициализация)
  - build          # Сборка приложения
  - test           # Тестирование
  - security       # Проверка безопасности
  - package        # Упаковка (Docker, архив)
  - deploy:stage   # Деплой на стейджинг
  - deploy:prod    # Деплой в продакшен
  - .post          # Пост-обработка (уведомления)
```

**Конкретные задания в каждой стадии:**

```yaml
# 1. BUILD - Сборка
build:
  stage: build
  script:
    - npm ci
    - npm run build
    - docker build -t my-app:$CI_COMMIT_SHA .

# 2. TEST - Все виды тестов
unit-tests:
  stage: test
  script: npm run test:unit

integration-tests:
  stage: test
  script: npm run test:integration

e2e-tests:
  stage: test
  script: npm run test:e2e

# 3. SECURITY - Безопасность
sast:            # Статический анализ безопасности
  stage: security
  script:
    - npm audit
    # или спец. инструменты: Snyk, Trivy, etc

dependency-check: # Проверка зависимостей
  stage: security
  script: check-dependencies

# 4. DEPLOY - Развертывание
deploy-to-staging:
  stage: deploy:stage
  script: ./deploy.sh staging
  environment: staging
  only: [main]

deploy-to-production:
  stage: deploy:prod
  script: ./deploy.sh production
  environment: production
  when: manual    # Ручное подтверждение для Delivery
  # when: always  # Автоматически для Deployment
```

### **🚀 Преимущества CI/CD**

1. **Скорость и частота релизов**
   - От месяцев/недель → до часов/минут
   - Примеры: Amazon - каждые 11.6 секунд, Netflix - тысячи деплоев в день

2. **Качество кода**
   - Автоматическое тестирование на каждом этапе
   - Раннее обнаружение багов
   - Стандартизация процессов

3. **Безопасность**
   - Автоматические проверки безопасности
   - Аудит всех изменений
   - Воспроизводимость сборок

4. **Продуктивность команды**
   - Меньше ручной работы
   - Быстрая обратная связь
   - Возможность сосредоточиться на разработке

### **🎯 Когда НЕ нужен CI/CD?**

| **Ситуация** | **Альтернатива** |
|--------------|------------------|
| Проект-прототип (1-2 разработчика) | Ручные деплои |
| Очень специфичное железо (embedded) | Кастомные скрипты |
| Релизы 1-2 раза в год | Традиционные процессы |
| Нет автоматических тестов | Сначала написать тесты |

### **📊 Метрики успеха CI/CD**

```yaml
# Что измерять в CI/CD:

lead_time:           # Время от коммита до прода
  target: < 1 часа   # (для Deployment)

deployment_frequency:# Частота релизов
  target: > 1 в день

change_failure_rate: # Процент неудачных деплоев
  target: < 5%

mean_time_to_recovery: # Время восстановления
  target: < 1 часа
```

### **🔄 Жизненный цикл CI/CD в GitLab**

```
Разработчик:
  1. git checkout -b feature/new-login
  2. Разрабатывает функционал
  3. git add . && git commit -m "Add login"
  4. git push origin feature/new-login

GitLab:
  5. Автоматически создает Merge Request
  6. Запускает пайплайн для этой ветки:
     - Сборка ✓
     - Юнит-тесты ✓
     - Интеграционные тесты ✓
     - Code review от коллег ✓
  
  7. После approval → Merge в main
  8. Запускается production пайплайн:
     - Сборка с новой версией
     - Полный прогон тестов
     - Развертывание в staging
     - (Авто или ручной) деплой в prod
```

### **💡 Best Practices CI/CD**

```yaml
# 1. Храните всё как код
# .gitlab-ci.yml, Dockerfile, deploy scripts

# 2. Быстрые пайплайны (< 10 минут для feedback)
cache:
  key: ${CI_COMMIT_REF_SLUG}
  paths:
    - node_modules/

# 3. Идемпотентность (повторный запуск = тот же результат)
deploy:
  script:
    - ansible-playbook deploy.yml  # Идемпотентный инструмент

# 4. Секреты через переменные, не в коде
# Settings → CI/CD → Variables (masked)

# 5. Разделение ответственности
stages:
  - build    # Ответственность Dev
  - test     # Ответственность QA
  - deploy   # Ответственность DevOps/SRE

# 6. Blue-Green или Canary деплой
deploy-blue:
  script: ./deploy.sh --strategy=blue-green

# 7. Откат при проблемах
rollback:
  script: ./rollback.sh
  when: on_failure
```

## **🏁 Заключение**

**CI/CD — это не просто инструменты, это культура и процессы:**

- **CI** = "Наш код всегда работает"
- **CD** = "Наш код всегда может быть у пользователей"

**Эволюция команды:**
1. **Ручные деплои** (начинаем здесь)
2. **Автоматическая сборка** (базовый CI)
3. **Автоматическое тестирование** (полноценный CI)
4. **Автоматический деплой на staging** (начало CD)
5. **Автоматический деплой в prod с ручным подтверждением** (Continuous Delivery)
6. **Полностью автоматический деплой в prod** (Continuous Deployment)

**Совет для начала:** Не пытайтесь сразу построить идеальный CI/CD. Начните с малого:
1. Автоматическая сборка при пуше
2. Добавьте 2-3 ключевых теста
3. Автоматизируйте деплой на тестовый сервер
4. Постепенно добавляйте новые этапы

**Помните:** Главная цель CI/CD — не "автоматизировать всё", а **ускорить обратную связь** и **снизить риски** при выпуске изменений.

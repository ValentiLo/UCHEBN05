## **GitLab CI/CD: Начало работы (Практическое руководство)**

### **Шаг 1: Подготовка проекта**

1. **Создайте новый проект в GitLab**
   - Зайдите в GitLab (gitlab.com или ваш корпоративный инстанс)
   - Нажмите "New project"
   - Выберите:
     - **Create blank project** (пустой проект)
     - Или **Import project**, если код уже есть в другом репозитории
   - Задайте имя проекта (например, `my-ci-cd-test`)

2. **Добавьте код в репозиторий**
   ```bash
   # Клонируйте проект
   git clone https://gitlab.com/ваш-username/my-ci-cd-test.git
   cd my-ci-cd-test
   
   # Создайте простой файл для тестирования
   echo "# My CI/CD Test Project" > README.md
   
   # Или если у вас уже есть проект, скопируйте его файлы в эту директорию
   ```

### **Шаг 2: Создайте базовый `.gitlab-ci.yml`**

1. **В корне проекта создайте файл `.gitlab-ci.yml`**:
   ```bash
   touch .gitlab-ci.yml
   ```

2. **Добавьте минимальную конфигурацию** (самый простой рабочий пример):
   ```yaml
   # .gitlab-ci.yml
   
   stages:
     - test
     - build
     - deploy
   
   # Простое задание для проверки окружения
   hello-world:
     stage: test
     script:
       - echo "Hello, GitLab CI/CD!"
       - echo "Мы находимся в папке: $(pwd)"
       - echo "Ветка: $CI_COMMIT_REF_NAME"
   
   # Задание для сборки (пример для простого скрипта)
   build-app:
     stage: build
     script:
       - echo "Начинаем сборку..."
       - echo "Сборка завершена!"
     artifacts:
       paths:
         - README.md  # Сохраняем README как артефакт
   
   # Ручное задание для развертывания
   deploy-to-stage:
     stage: deploy
     script:
       - echo "Развертывание на стейджинг..."
       - echo "Представьте, что здесь команды деплоя"
     when: manual  # Требует ручного запуска
     only:
       - main      # Только для ветки main/master
   ```

### **Шаг 3: Первый коммит и запуск пайплайна**

1. **Добавьте файлы и сделайте коммит:**
   ```bash
   git add .
   git commit -m "Add basic CI/CD configuration"
   git push origin main  # или master
   ```

2. **Наблюдайте за запуском пайплайна:**
   - Перейдите в ваш проект в GitLab
   - В левом меню выберите **CI/CD → Pipelines**
   - Вы увидите запущенный пайплайн со статусом `pending` или `running`

3. **Исследуйте пайплайн:**
   - Нажмите на статус пайплайна
   - Вы увидите три стадии: `test`, `build`, `deploy`
   - Задания `hello-world` и `build-app` выполнятся автоматически
   - Задание `deploy-to-stage` будет ждать ручного запуска (синяя кнопка ▶️)

### **Шаг 4: Проверьте результаты**

1. **Просмотрите логи выполнения:**
   - Кликните на любое выполненное задание (например, `hello-world`)
   - Вы увидите вывод команд, которые выполнялись на раннере
   - В логах будут строки: `Hello, GitLab CI/CD!` и другие echo

2. **Посмотрите артефакты:**
   - В задании `build-app` нажмите на вкладку **"Artifacts"**
   - Скачайте архив и убедитесь, что там есть `README.md`

### **Шаг 5: Добавьте реальную логику (примеры)**

#### **Пример 1: Для Node.js проекта**
```yaml
image: node:16-alpine  # Используем конкретный Docker-образ

stages:
  - install
  - test
  - build

cache:  # Кэшируем node_modules для ускорения
  paths:
    - node_modules/

install-dependencies:
  stage: install
  script:
    - npm ci --only=production
  artifacts:
    paths:
      - node_modules/

run-tests:
  stage: test
  script:
    - npm test
  dependencies:
    - install-dependencies

build-project:
  stage: build
  script:
    - npm run build
  artifacts:
    paths:
      - dist/  # Папка с собранным проектом
```

#### **Пример 2: Для Python проекта**
```yaml
image: python:3.9-slim

stages:
  - test
  - deploy

before_script:
  - python --version
  - pip install -r requirements.txt

run-pytest:
  stage: test
  script:
    - pytest --junitxml=report.xml
  artifacts:
    reports:
      junit: report.xml  # GitLab покажет отчет о тестах

deploy-heroku:
  stage: deploy
  script:
    - echo "Деплой на Heroku..."
    # - git push heroku main
  only:
    - main
```

### **Шаг 6: Настройте раннер (если нужно)**

По умолчанию GitLab использует **Shared Runners** (они уже настроены на gitlab.com).

**Если вам нужны специфичные раннеры:**

1. **Для GitLab.com:**
   - В проекте: **Settings → CI/CD → Runners**
   - Вы увидите "Set up a specific Runner manually"
   - Следуйте инструкциям для установки GitLab Runner на ваш сервер

2. **Для self-hosted GitLab:**
   ```bash
   # Установите GitLab Runner
   # Для Ubuntu/Debian:
   curl -L https://packages.gitlab.com/install/repositories/runner/gitlab-runner/script.deb.sh | sudo bash
   sudo apt-get install gitlab-runner
   
   # Зарегистрируйте раннер
   sudo gitlab-runner register
   # Вам понадобится URL и registration token из:
   # Проект → Settings → CI/CD → Runners
   ```

### **Шаг 7: Полезные команды для отладки**

1. **Проверка синтаксиса .gitlab-ci.yml:**
   - В GitLab: **CI/CD → Editor** (есть встроенный валидатор)
   - Локально: `gitlab-ci-validate` (установите через pip или gem)

2. **Локальный запуск заданий (с GitLab Runner):**
   ```bash
   # Установите gitlab-runner локально
   gitlab-runner exec docker hello-world
   ```

### **Частые проблемы и решения**

| Проблема | Решение |
|----------|---------|
| Пайплайн не запускается | Проверьте, что файл называется именно `.gitlab-ci.yml` и в корне |
| "No stages/jobs" | Убедитесь, что в файле есть секция `stages` и хотя бы одно задание |
| Задания "зависли" в pending | Проверьте доступность раннеров в **Settings → CI/CD → Runners** |
| Ошибки в скриптах | Смотрите логи выполнения, добавьте `set -x` для отладки |

### **Следующие шаги после начала:**

1. **Добавьте тесты** в ваш проект
2. **Настройте кэширование** для ускорения сборок
3. **Используйте переменные окружения** (**Settings → CI/CD → Variables**)
4. **Настройте уведомления** о результатах пайплайнов
5. **Создайте Merge Request pipeline** для проверки кода перед слиянием

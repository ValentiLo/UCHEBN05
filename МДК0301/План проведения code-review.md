# План проведения code-review

## 1. Общие положения

**Code-review** (рецензирование кода) — процесс проверки исходного кода автора другими участниками команды с целью:
- выявления ошибок и уязвимостей;
- улучшения читаемости и поддерживаемости кода;
- соблюдения стандартов кодирования;
- обмена знаниями между разработчиками.

---

## 2. Участники процесса

| Роль | Ответственность |
|------|----------------|
| **Автор** | Пишет код, создаёт запрос на проверку (Pull Request/Merge Request), исправляет замечания |
| **Рецензент (1–2 человека)** | Проверяет код по чек-листу, оставляет комментарии, утверждает изменения |
| **Технический лид (опционально)** | Разрешает спорные ситуации, утверждает критически важные изменения |

---

## 3. Инструменты

| Инструмент | Назначение |
|------------|------------|
| **GitHub / GitLab** | Хостинг репозитория, Pull Requests, обсуждения |
| **Flake8 / pylint** | Автоматическая проверка стиля кода (PEP 8) |
| **mypy** | Проверка аннотаций типов |
| **pytest** | Запуск автоматических тестов |
| **SonarLint / Qodana** | Дополнительный статический анализ |
| **Telegram / Slack** | Уведомления о новых проверках |

## 4. Критерии проверки (чек-лист)

### 4.1. Функциональность и логика
- [ ] Код решает поставленную задачу?
- [ ] Нет логических ошибок, бесконечных циклов, неверных условий?
- [ ] Корректно обрабатываются граничные случаи (пустые списки, нули, None)?

### 4.2. Обработка ошибок
- [ ] Проверяются ли входные данные?
- [ ] Обрабатываются ли исключения (`try-except`)?
- [ ] Нет ли скрытых ошибок (деление на ноль, выход за границы списка)?

### 4.3. Стиль и читаемость
- [ ] Код соответствует **PEP 8** (отступы, пробелы, длина строк)?
- [ ] Имена переменных, функций, классов понятны и отражают суть?
- [ ] Нет «магических чисел» — используются именованные константы?

### 4.4. Документация
- [ ] Есть ли **docstring** у каждой функции/класса?
- [ ] Сложные участки кода снабжены комментариями?
- [ ] Есть ли общая документация по проекту (README)?

### 4.5. Архитектура и дизайн
- [ ] Соблюдается ли принцип **DRY** (Don't Repeat Yourself)?
- [ ] Функции слишком длинные? (рекомендуется не более 30-50 строк)
- [ ] Код разбит на логические модули/классы?

### 4.6. Производительность
- [ ] Нет неэффективных алгоритмов (вложенные циклы там, где можно обойтись словарём)?
- [ ] Ресурсы (файлы, соединения с БД) закрываются?
- [ ] Нет лишних запросов к БД или API?

### 4.7. Безопасность
- [ ] Нет уязвимостей (SQL-инъекции, XSS, открытые пароли в коде)?
- [ ] Используется ли параметризованные запросы вместо конкатенации строк?
- [ ] Валидируются ли данные от пользователя?

### 4.8. Тестирование
- [ ] Написаны ли **unit-тесты** для ключевых функций?
- [ ] Проходят ли все существующие тесты после изменений?
- [ ] Есть ли тесты на граничные случаи?

### 4.9. Типизация
- [ ] Используются ли аннотации типов (type hints)?
- [ ] Аннотации соответствуют реальным типам данных?

## 5. Процесс проведения code-review

### Этап 1. Подготовка (автор)
1. Убедиться, что код работает локально и тесты проходят.
2. Запустить автоматические линтеры (Flake8, mypy).
3. Устранить все замечания автоматических проверок.
4. Создать **Pull Request** (PR) или **Merge Request** (MR) в системе контроля версий.
5. В описании PR указать:
   - что сделано;
   - какие тесты проводились;
   - если есть спорные моменты — отметить их.
6. Назначить рецензентов (не менее 1, желательно 2).

### Этап 2. Проверка (рецензент)
1. Ознакомиться с описанием PR.
2. Запустить код локально (по необходимости).
3. Проверить код по чек-листу (раздел 4).
4. Оставить комментарии:
   - **Блокирующие** (обязательны к исправлению) — критичные ошибки, нарушение безопасности, неработающая логика.
   - **Некритичные** (рекомендации) — стиль, переименование, мелкие улучшения.
5. Вынести вердикт:
   - **Approved** (одобрено) — можно сливать.
   - **Changes requested** (требуются изменения) — автор должен исправить.
   - **Comment** (комментарии без блокировки) — замечания на усмотрение автора.

### Этап 3. Доработка (автор)
1. Исправить все блокирующие замечания.
2. Ответить на комментарии (принять / объяснить, почему не исправлено).
3. Запушить исправления в тот же PR.
4. Запросить повторную проверку.

### Этап 4. Утверждение и слияние
1. Рецензент проверяет исправления.
2. Если все замечания устранены — ставит **Approved**.
3. Автор (или технический лид) выполняет **merge** (слияние) в целевую ветку.
4. Удалить ветку с изменениями (опционально).

### Этап 5. Пост-релиз (опционально)
- Через 1–2 недели провести ретроспективу: какие ошибки чаще всего находили, что можно улучшить в процессе.

## 7. Критерии готовности PR к проверке

- [ ] Ветка актуальна относительно целевой ветки (`main`/`develop`) — нет конфликтов.
- [ ] CI/CD пайплайн (тесты, линтеры) зелёный (успешный).
- [ ] Размер PR не превышает **400 строк кода** (большие PR разбиваются на несколько).
- [ ] В описании указано, что изменилось и зачем.

---

## 8. Что запрещено при code-review

| Запрещено | Почему |
|-----------|--------|
| Личные оскорбления и токсичные комментарии | Уважение к коллегам |
| Проверка кода «по диагонали» (поверхностно) | Пропускаются ошибки |
| Затягивание проверки более 2 дней | Блокирует работу команды |
| Изменение кода рецензентом напрямую в PR автора (без комментария) | Нарушает авторство |
| Требование изменить стиль, если он соответствует принятому стандарту | Субъективные придирки |

## 9. Пример комментария к PR

> **Автор:** Иванов Иван  
> **PR:** Добавлена функция валидации email  
> **Рецензент:** Петров Пётр  

**Комментарий:**
> Строка 15: `if '@' in email:` — этого недостаточно для валидации email. Нужно также проверить наличие точки после @.  
> **Тип:** блокирующий (может пропустить некорректные email).  
> **Предложение:** использовать регулярное выражение или встроенную проверку.

## 10. Метрики эффективности code-review (для отчёта)

| Метрика | Формула | Целевое значение |
|---------|---------|------------------|
| Покрытие ревью | (число PR с ревью / общее число PR) × 100% | ≥ 95% |
| Среднее время до первого комментария | сумма времени / число PR | ≤ 24 ч |
| Доля критических замечаний | (критические / общее число) × 100% | ≤ 20% |
| Процент возвратов на доработку | (PR с changes requested / общее число) × 100% | ≤ 30% |

# **МДК 05.01 Практическое занятие 4: Назначение технической документации**

## **Цель занятия:**
Понять назначение, виды и правила оформления технической документации в IT-проектах.

---

## **1. Что такое техническая документация?**

### **Определение:**
Техническая документация (ТД) — это **совокупность документов**, описывающих:
- Как устроена система
- Как ее разрабатывать, тестировать и использовать
- Как сопровождать и развивать

### **Простая аналогия:**
```
Техническая документация для ПО = 
Инструкция + Чертеж + Паспорт + Руководство
```

---

## **2. Виды технической документации**

### **А) По этапам жизненного цикла ПО:**

```
1. ДО разработки (предпроектная)
   ├── Техническое задание (ТЗ)
   ├── Бизнес-требования (BRD)
   ├── Технико-экономическое обоснование (ТЭО)
   └── План проекта

2. ВО ВРЕМЯ разработки (проектная)
   ├── Технический проект
   ├── Спецификации
   ├── Прототипы
   └── Диаграммы UML/BPMN

3. ПОСЛЕ разработки (эксплуатационная)
   ├── Руководство пользователя
   ├── Руководство администратора
   ├── Инструкции по установке
   └── Описание API
```

### **Б) По назначению:**

| Тип документа | Для кого | Что содержит |
|--------------|----------|--------------|
| **Техническое задание (ТЗ)** | Заказчик, разработчик | Что нужно сделать, требования |
| **Технический проект** | Разработчики, тестировщики | Как будет сделано, архитектура |
| **Руководство пользователя** | Конечные пользователи | Как пользоваться системой |
| **Руководство администратора** | Системные администраторы | Как устанавливать и настраивать |
| **API-документация** | Другие разработчики | Как работать с API системы |
| **Тест-планы** | Тестировщики | Что и как тестировать |

## **3. Ключевые документы (разбираем подробно)**

### **Документ 1: Техническое задание (ТЗ)**

**Назначение:**  
Определить ЧТО нужно сделать, чтобы заказчик и исполнитель понимали задачу одинаково.

**Структура ТЗ (по ГОСТ 34):**
```markdown
# ТЕХНИЧЕСКОЕ ЗАДАНИЕ
## на разработку [Название системы]

### 1. Основания для разработки
- Договор № ___ от ___
- Приказ № ___ от ___

### 2. Назначение системы
[Для чего нужна система, какие задачи решает]

### 3. Требования к системе
#### 3.1. Функциональные требования
- FR1: [Функция 1]
- FR2: [Функция 2]

#### 3.2. Требования к надежности
- Время безотказной работы: 99.5%
- Восстановление после сбоя: не более 1 часа

#### 3.3. Условия эксплуатации
- Количество пользователей: 100
- Рабочие места: 50

### 4. Стадии и этапы разработки
- Анализ: 01.03-15.03
- Разработка: 16.03-30.04
- Тестирование: 01.05-15.05

### 5. Порядок контроля и приемки
[Как заказчик будет принимать работу]

### 6. Приложения
[Эскизы, схемы, примеры]
```

**Пример плохого ТЗ:**  
> "Сделать удобный сайт для магазина"

**Пример хорошего ТЗ:**  
> "Разработать интернет-магазин с каталогом 1000 товаров, корзиной, оплатой через Сбербанк, личным кабинетом пользователя. Система должна выдерживать 1000 посетителей одновременно."

### **Документ 2: Технический проект**

**Назначение:**  
Описать КАК будет реализована система.

**Содержание:**
```
1. Архитектура системы
   ├── Схема компонентов
   ├── Выбор технологий
   └── Описание взаимодействий

2. Диаграммы
   ├── Use Case (прецедентов)
   ├── Sequence (последовательностей)
   ├── Class (классов)
   └── Database (базы данных)

3. Описание модулей
   ├── Модуль авторизации
   ├── Модуль заказов
   └── Модуль отчетов

4. Интерфейсы
   ├── API-методы
   ├── Форматы данных
   └── Протоколы обмена
```

### **Документ 3: Руководство пользователя**

**Назначение:**  
Научить пользователя работать с системой.

**Структура:**
```markdown
# Руководство пользователя
## Система "Учет товаров"

### 1. Начало работы
#### 1.1. Вход в систему
1. Откройте браузер
2. Перейдите по адресу: http://system.ru
3. Введите логин и пароль
4. Нажмите "Войти"

[СКРИНШОТ: Форма входа]

### 2. Основные операции
#### 2.1. Добавление товара
1. Нажмите "Товары" → "Добавить"
2. Заполните форму...
```

**Принципы хорошего руководства:**
- Много скриншотов
- Пошаговые инструкции
- Примеры из реальной работы
- Устранение типовых проблем

### **Документ 4: API-документация**

**Пример (OpenAPI/Swagger):**
```yaml
openapi: 3.0.0
info:
  title: API магазина
  version: 1.0.0

paths:
  /api/products:
    get:
      summary: Получить список товаров
      parameters:
        - name: category
          in: query
          schema:
            type: string
      responses:
        '200':
          description: Успешно
          content:
            application/json:
              schema:
                type: array
                items:
                  $ref: '#/components/schemas/Product'
```

## **4. Практическое задание**

### **Задача:**  
Вы - разработчик, получили задачу создать систему учета студентов для колледжа.  
Нужно подготовить фрагменты технической документации.

### **Задание 1: Составьте ТЗ (фрагмент)**

```markdown
# ТЕХНИЧЕСКОЕ ЗАДАНИЕ
## на разработку системы "Электронный журнал колледжа"

### 3. Требования к системе

#### 3.1. Функциональные требования:
- FR1: Ведение списка студентов
  - Добавление/редактирование/удаление студентов
  - Хранение ФИО, группы, фото, контактов
  
- FR2: Ведение расписания
  - Создание расписания на семестр
  - Назначение преподавателей
  
- FR3: Выставление оценок
  - Преподаватель выставляет оценки за занятия
  - Расчет среднего балла
  
- FR4: Формирование отчетов
  - Ведомость успеваемости по группе
  - Статистика посещаемости

#### 3.2. Требования к надежности:
- Система должна быть доступна 24/7, кроме воскресенья 03:00-05:00 (техобслуживание)
- Резервное копирование данных: ежедневно в 23:00
- Восстановление после сбоя: не более 30 минут

#### 3.3. Требования к интерфейсу:
- Веб-интерфейс, адаптивный дизайн
- Поддержка браузеров: Chrome 80+, Firefox 75+
- Язык интерфейса: русский
```

### **Задание 2: Создайте диаграмму Use Case**

```
[Преподаватель] ---> (Выставить оценку)
                      |
                      V
                (Посмотреть успеваемость)
                      ^
                      |
[Студент] -----------> (Посмотреть свои оценки)
                      |
                      V
[Администратор] ---> (Добавить студента)
                      |
                      V
                (Сформировать отчет)
```

**Заполните таблицу акторов:**

| Актор | Описание | Примеры действий |
|-------|----------|------------------|
| Студент | Обучающийся в колледже | Посмотреть расписание, оценки |
| Преподаватель | Преподает дисциплины | Выставить оценки, посмотреть посещаемость |
| Администратор | Управляет системой | Добавить пользователя, настроить права |
| Бухгалтер | Начисляет стипендию | Посмотреть успеваемость для расчета |

### **Задание 3: Напишите фрагмент руководства пользователя**

```markdown
# Руководство пользователя
## Раздел: Выставление оценок (для преподавателя)

### 1. Как выставить оценку студенту

#### Шаг 1: Откройте журнал группы
1. Войдите в систему под своим логином
2. В главном меню выберите "Журналы"
3. Найдите нужную группу (например, "ИСП-201")
4. Нажмите на название группы

[СКРИНШОТ: Список групп]

#### Шаг 2: Выберите занятие
1. Вверху страницы выберите дату занятия
2. Или найдите занятие в календаре
3. Нажмите на нужное занятие

#### Шаг 3: Выставьте оценку
1. Найдите студента в списке
2. В графе "Оценка" введите цифру от 2 до 5
3. При необходимости добавьте комментарий
4. Нажмите "Сохранить"

[СКРИНШОТ: Форма выставления оценки]

### 2. Частые проблемы и решения

#### Проблема: Не вижу нужную группу
Решение:
1. Проверьте, назначены ли вы преподавателем этой группы
2. Обратитесь к администратору

#### Проблема: Не могу изменить старую оценку
Решение:
1. Оценки старше 2 недель изменяются только через администратора
2. Напишите заявление в учебную часть
```

## **5. Стандарты и ГОСТы**

### **Основные стандарты:**
```markdown
ГОСТ 34.201-89
├── Виды, комплектность и обозначение документов
└── Обязательные документы для автоматизированных систем

ГОСТ 19.ххх (ЕСПД)
├── Единая система программной документации
└── Для программного обеспечения

ISO/IEC/IEEE 12207
├── Международный стандарт
└── Процессы жизненного цикла ПО

IEEE 1016
└── Стандарт для описания архитектуры ПО
```

### **Пример оформления по ГОСТ:**
```
Код документа: ТЗ 34.01-2023-01
Где:
- ТЗ — вид документа (Техническое задание)
- 34 — код системы (по ГОСТ 34)
- 01 — порядковый номер в системе
- 2023 — год создания
- 01 — версия документа
```

## **7. Роль технического писателя**

### **Чем занимается техписатель:**
```
1. Анализ аудитории
   ├── Кто будет читать?
   ├── Какой уровень знаний?
   └── Что им нужно знать?

2. Структурирование информации
   ├── От общего к частному
   ├── Логическая последовательность
   └── Удобная навигация

3. Написание и оформление
   ├── Простой понятный язык
   ├── Единый стиль
   └── Визуализация (скриншоты, диаграммы)

4. Актуализация
   ├── Обновление при изменениях
   ├── Удаление устаревшего
   └── Сбор обратной связи
```

### **Принципы хорошей документации:**
- **KISS** (Keep It Simple, Stupid) — просто и понятно
- **DRY** (Don't Repeat Yourself) — не повторяйся
- **Сначала цель, потом детали** — скажи что делать, потом как
- **Примеры важнее описаний** — покажи, как работает

## **8. Практические советы для разработчиков**

### **Совет 1: Документируйте по ходу разработки**
```
ПЛОХО:
Разработал → Протестировал → Сдал → Вспомнил про документацию

ХОРОШО:
Разработал → Задокументировал → Протестировал → Скорректировал → Сдал
```

### **Совет 2: Используйте шаблоны**
Создайте шаблоны для:
- Технического задания
- README-файлов
- Комментариев в коде
- API-документации

### **Совет 3: Автоматизируйте**
```yaml
# Пример автоматической генерации документации

tools:
  - JSDoc: # для JavaScript
    command: "jsdoc src -d docs"
    
  - Sphinx: # для Python
    command: "sphinx-build docs/source docs/build"
    
  - Swagger: # для API
    command: "swagger-jsdoc -d swaggerDef.js -o swagger.json"
```

### **Совет 4: Проверяйте на реальных пользователях**
Дайте документацию:
1. Коллеге-разработчику (проверит техническую часть)
2. Тестировщику (проверит полноту)
3. Начинающему сотруднику (проверит понятность)

## **9. Критерии качества документации**

### **Чек-лист проверки:**
```markdown
# Чек-лист качества техдокументации

## Содержание
- [ ] Есть оглавление
- [ ] Логическая структура
- [ ] Все разделы заполнены

## Текст
- [ ] Нет орфографических ошибок
- [ ] Простой понятный язык
- [ ] Нет жаргонизмов (или объяснены)

## Примеры
- [ ] Есть примеры использования
- [ ] Примеры рабочие и актуальные
- [ ] Скриншоты там, где нужно

## Актуальность
- [ ] Соответствует текущей версии
- [ ] Указана версия документа
- [ ] Есть дата последнего обновления

## Дизайн
- [ ] Единый стиль оформления
- [ ] Удобочитаемые шрифты
- [ ] Цветовая схема не мешает чтению
```

### **Пример оценки документации:**
```
Отлично (5):
├── Полное описание системы
├── Примеры для всех функций
├── Актуальные скриншоты
├── Нет технических ошибок
└── Удобная навигация

Хорошо (4):
├── Основные функции описаны
├── Есть примеры
├── Мало скриншотов
└── Небольшие неточности

Удовлетворительно (3):
├── Описаны только ключевые функции
├── Нет примеров
├── Устаревшие скриншоты
└── Есть ошибки
```

## **10. Домашнее задание**

### **Задание:**  
Подготовить полный комплект документации для модуля "Личный кабинет студента" в системе "Электронный журнал".

### **Что нужно сделать:**
1. **Техническое задание** на модуль (1 страница)
2. **Диаграмму Use Case** для модуля
3. **Руководство пользователя** для студента (2 раздела)
4. **Описание API** для одного метода (например, "Получить успеваемость")

### **Пример структуры API:**
```json
{
  "method": "GET",
  "endpoint": "/api/students/{id}/grades",
  "description": "Получить оценки студента",
  "parameters": [
    {
      "name": "id",
      "type": "integer",
      "required": true,
      "description": "ID студента"
    },
    {
      "name": "semester",
      "type": "string",
      "required": false,
      "description": "Номер семестра (например, '2023-1')"
    }
  ],
  "response": {
    "200": {
      "description": "Успешно",
      "schema": {
        "type": "object",
        "properties": {
          "student": {"type": "string"},
          "grades": {"type": "array", "items": {"type": "object"}}
        }
      }
    }
  }
}
```

### **Критерии оценки домашнего задания:**
1. **Полнота** (все пункты выполнены) — 40%
2. **Качество описания** (понятно, без ошибок) — 30%
3. **Соответствие стандартам** — 20%
4. **Оформление** (структура, читаемость) — 10%

## **Ключевые выводы с занятия:**

1. **Техдокументация — это не "бумажная волокита"**, а инструмент:
   - Коммуникации между заказчиком и разработчиком
   - Обучения пользователей
   - Сопровождения и развития системы

2. **Хорошая документация экономит время:**
   - Меньше вопросов от пользователей
   - Быстрее ввод новых сотрудников
   - Проще вносить изменения

3. **Документировать нужно ВСЕГДА**, даже для маленьких проектов

4. **Лучшая документация** — та, которую читают и используют

**Запомните:**  
"Программу без документации невозможно поддерживать.  
Хорошую программу без документации невозможно использовать.  
Отличную программу без документации невозможно понять."

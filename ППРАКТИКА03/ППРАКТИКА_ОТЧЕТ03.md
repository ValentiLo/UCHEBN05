### **Рекомендуемая структура отчёта по практике для ПМ.03**

**Титульный лист** (форма колледжа).

**Содержание.**

#### **1. Введение**
*   **Цель практики:** Приобретение практического опыта в ревьюировании программного кода и анализе характеристик программных продуктов в рамках ПМ.03.
*   **Задачи практики:**
    1.  Освоить методы и инструменты статического анализа и ревью кода.
    2.  Провести инспектирование программного кода на соответствие технической документации и стандартам.
    3.  Выполнить измерение метрик качества кода с использованием специализированных средств (Visual Studio, сторонние анализаторы).
    4.  Провести сравнительный анализ программных продуктов или инструментов разработки.
*   **Объект практики:** Процесс разработки и сопровождения программного обеспечения в [Название компании/Учебный проект].
*   **Предмет практики:** Процедуры ревьюирования и анализа программного кода проекта [Название проекта, например, "Веб-приложение для учёта заказов"].
*   **Место и сроки прохождения.**

#### **2. Основная часть**

**Глава 1. Организация и планирование работ по ревьюированию (Соответствует ПК 3.1)**
*   **1.1. Анализ технической документации:** Описание изученных документов (ТЗ, спецификации, стандарты кодирования компании, архитектурное описание).
*   **1.2. Разработка алгоритма и плана ревью (Code-Review Planning):**
    *   Определение объёма кода для ревью (модуль, pull request).
    *   Выбор типа ревью (формальная инспекция, сквозной просмотр, pair programming).
    *   Составление чек-листа для ревьюера на основе требований ТЗ и стандартов.
    *   **Алгоритм проведения ревью:** Пошаговое описание (получение кода → подготовка → проведение анализа → фиксация замечаний → обсуждение → переработка → верификация).
*   **1.3. Обратное проектирование (Reverse Engineering) алгоритма:** Восстановление логики работы модуля по исходному коду для понимания его работы перед ревью. Привести полученную блок-схему или описание алгоритма.

**Глава 2. Проведение инспектирования кода и выявление дефектов (Соответствует ПК 3.1, ПК 3.3)**
*   **2.1. Инспектирование кода (Code Inspection):**
    *   **Методология:** Описание применённого подхода (например, проверка на соответствие PEP 8, Google Style Guide, внутренним стандартам).
    *   **Инструменты:** Использование статических анализаторов (например, SonarQube, Pylint, ReSharper) как вспомогательного средства.
*   **2.2. Классификация выявленных замечаний:**
    *   **Ошибки и недочёты логики:** Примеры с фрагментами кода (ошибка в условии цикла, неправильная обработка граничных значений).
    *   **Отклонения от алгоритма:** Несоответствие реализации заявленному в ТЗ или восстановленному алгоритму.
    *   **Нарушения стиля (Code Style Violations):** Несоблюдение отступов, именования переменных/функций, длины строк. Таблица примеров.
    *   **Потенциальные уязвимости безопасности (Security Issues):** Например, риск SQL-инъекции, небезопасная работа с памятью (если применимо).
*   **2.3. Оформление отчёта о ревью:** Пример оформления замечаний в системе (GitHub/GitLab Comments, JIRA). Привести скриншот.

**Глава 3. Измерение характеристик кода и сравнительный анализ (Соответствует ПК 3.2, ПК 3.4)**
*   **3.1. Измерение характеристик кода в среде Visual Studio:**
    *   **Используемые метрики:** Цикломатическая сложность (Cyclomatic Complexity), объём кода (Lines of Code), индекс поддерживаемости (Maintainability Index), глубина наследования, классовые связи.
    *   **Процесс измерения:** Описание, как запускался анализ (например, встроенный Code Metrics Calculator, NDepend).
    *   **Результаты и их интерпретация:** Таблица с метриками для ключевых модулей. Анализ: "Модуль X имеет высокую цикломатическую сложность (25), что указывает на переусложнённую логику и трудность тестирования. Рекомендация: провести рефакторинг."
*   **3.2. Выявление ошибок и недочётов программного продукта на основе метрик:** Связь между плохими метриками и реальными проблемами (например, модуль с низким индексом поддерживаемости содержал больше всего багов).
*   **3.3. Сравнительный анализ программных продуктов/средств разработки (ПК 3.4):**
    *   **Постановка задачи:** Сравнить два подхода/библиотеки/инструмента для решения одной задачи из ТЗ (например, REST-фреймворки: Django REST vs FastAPI).
    *   **Критерии сравнения:** Определены на основе ТЗ (производительность, простота разработки, сообщество, документация).
    *   **Методика сравнения:** Обзор документации, создание прототипов, бенчмаркинг (если применимо).
    *   **Результаты и рекомендации:** Сводная таблица по критериям и обоснованный вывод о выборе наилучшего решения для проекта.
